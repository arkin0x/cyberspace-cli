# Golden vectors

Cross-implementation consensus locks: files here are loaded by the Python tests in this repository and are meant to be copied, unchanged, into the TypeScript ports (cyberspace-cli-js, ONOSENDAI) and checked there. A port agrees with this implementation when it gives every vector the expected verdict.

## `chain-rules-2026-09-28-virtual-brackets.json`

The chain rules of `CYBERSPACE_V2.md` section 8.12 at revision `2026-09-28-virtual-brackets` (arkin0x/cyberspace `df00a48`): active chain resolution (8.7.3), skipping actions a verifier does not recognize (8.9), virtual brackets (8.11), and the chain rules of DECK-0001, which is mandatory at this revision. Generated by `scripts/gen_chain_vectors.py`; checked by `tests/test_chain_rules.py`. Regenerating writes the same file byte for byte.

### Top level

| Key | Meaning |
|---|---|
| `chain_rules_revision` | The revision the vectors lock. A verifier SHOULD report the revision it implements (8.12). |
| `spec` | The spec repository and commit the vectors were written against. |
| `verify_with` | How to run each vector: `check_signatures: true`, and the line below as the only block data. Before resolving, a verifier sets aside every event that is not authentic (its id is not its NIP-01 hash, or its sig does not verify), because anyone can publish one and it must not be able to win a fork. Vectors whose names end in `-ignored` contain such events. |
| `test_key` | The secret key that signed every event, its pubkey, and how it was chosen. Never use it for anything else. |
| `game_pubkey` | The game pubkey the brackets name in their `p` tags. |
| `line.blocks` | Synthetic Bitcoin blocks 0 to 7: `height`, `block_hash` and `merkle_root` (lowercase hex, display order), and `coord`, the stop coordinate derived per DECK-0001 section 1. Every stop is a port (plane bit 1), so `coord` equals `merkle_root`. The tip is 7: a height above it does not exist. |
| `reasons` | Every reason code, with the rule it names. |
| `vectors` | The vectors. |

### A vector

| Key | Meaning |
|---|---|
| `name` | Unique, stable. |
| `spec` | The sections the vector exercises. |
| `description` | What the vector shows, in words. |
| `open_question` | Present when the verdict rests on a reading of the spec that is still open. A port should match it, and the vector will change if the spec says otherwise. |
| `events` | Complete signed NIP-01 events (`id`, `pubkey`, `created_at`, `kind`, `tags`, `content`, `sig`), kind 3333, all by `test_key.pubkey`. Their order is not meaningful: a verifier must resolve them per 8.7.3, and some vectors list them out of order on purpose. Events that are not on the active chain (an older chain, the losing branch of a fork) are included where the vector is about ignoring them. |
| `expected` | The verdict. |

A valid verdict:

```json
{"valid": true, "chain": ["<id>", "..."], "position": "<coord hex>", "head": "<id>", "open_bracket": null, "skipped": []}
```

- `chain`: the ids of the active chain in order, the spawn first.
- `position`: the identity's position in cyberspace: the `C` of the last recognized action (8.9 step 5), or the `c` of the `enter-virtual` left open at the head (8.11.4 rule 7).
- `head`: the id of the last event of the active chain, which may be a skipped action.
- `open_bracket`: the id of the `enter-virtual` open at the head, else `null`.
- `skipped`: the ids of the actions skipped under 8.9, in chain order. Names inside a bracket are virtual actions and are never listed here.

An invalid verdict:

```json
{"valid": false, "chain": ["<id>", "..."], "reason": "<code>", "invalid_at": "<id>", "invalid_index": 3}
```

- `invalid_at` and `invalid_index`: the first event on the active chain that breaks a rule, and its index in `chain` (the spawn is 0). The chain is invalid from that event.
- `reason`: one code from `reasons`.
- When no spawn exists, `chain` is empty and `invalid_at` and `invalid_index` are `null`, with reason `no-spawn`.

Each invalid vector breaks exactly one rule, so the order in which a verifier runs its checks on an event does not change the reason. The free-text detail a verifier prints is not part of the vectors.

The vectors do not lock where an identity with an invalid chain stands. The Python verdict reports the position carried up to the failing event as `last_valid_position`, but section 3.2 also describes an invalid chain as a derezz (back at the spawn), and the spec does not choose between them.

### What it costs to run them

Every proof in the vectors is real and checked in full: hops (8.7.1), sidesteps at Level 1 (8.7.2), entry proofs (DECK-0001 3.2) and rides at Level 1 (DECK-0001 5.5). They are kept cheap by construction: the test key was chosen so its spawn has a terrain K of at most 3, every move flips one low bit (spatial trees of height 1), every stop has a terrain K of at most 3, every block's ride leaf is a tree of height at most 10, and every ride is one or two blocks long (re-roll price A = 1). A ride check still replays one height-16 Cantor tree for its price, about a second in pure Python; the whole file verifies in about ten seconds.

### Where the vectors should live

They are here because the reference implementation generates them and runs them on every test run, and because the other vector files the ports already copy (`tests/fixtures/sidestep_v3.json`, `avatar_work.json`) come from this repository. The chain rules are the spec's, not this implementation's, so once the readings marked `open_question` are settled the file should also be published in arkin0x/cyberspace next to the revision it locks, with this repository and the ports pinned to that copy, as the sidestep and ride references are.
