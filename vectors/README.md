# Golden vectors

Cross-implementation consensus locks: files here are loaded by the Python tests in this repository and are meant to be copied, unchanged, into the TypeScript ports (cyberspace-cli-js, ONOSENDAI, cyberspace-relay) and checked there. A port agrees with this implementation when it gives every vector the expected verdict.

## `chain-rules-2026-09-28-virtual-brackets.json`

The chain rules of `CYBERSPACE_V2.md` section 8.12 at revision `2026-09-28-virtual-brackets`, with the rulings folded in on 2026-10-07 and in two rounds on 2026-10-08 (arkin0x/cyberspace `1bf5694`; the second round of 2026-10-08 made a fork fatal, any `A` tag equal to `spawn` a spawn, a spawn never a link, every read tag exactly once, and the network Bitcoin mainnet, always): authentic events only and active chain resolution with a fatal fork (8.7.3), every read tag exactly once, frozen chains at their last valid position (3.2, 8.7.3), exactly one `A` tag (8.8), skipping actions a verifier does not recognize (8.9), opaque virtual brackets (8.11), sector tags (10), and the chain rules of DECK-0001, which is mandatory at this revision. Generated by `scripts/gen_chain_vectors.py`; checked by `tests/test_chain_rules.py`. Regenerating writes the same file byte for byte.

### Top level

| Key | Meaning |
|---|---|
| `chain_rules_revision`, `revision_note` | The revision the vectors lock, and which rulings it includes. A verifier SHOULD report the revision it implements (8.12). |
| `spec` | The spec repository and commit the vectors were written against. |
| `verify_with` | How to run each vector: `identity` is the pubkey whose chain is resolved, and `line.blocks` is the only block data. |
| `test_key` | The secret key that signed the identity's events, its pubkey, and how it was chosen. Never use it for anything else. |
| `other_key` | The pubkey of another author, whose event one vector includes to show it is discarded. |
| `game_pubkey` | The game pubkey the brackets name in their `p` tags. |
| `line.blocks` | Synthetic Bitcoin blocks 0 to 7: `height`, `block_hash` and `merkle_root` (lowercase hex, display order), and `coord`, the stop coordinate derived per DECK-0001 section 1. Every stop is a port (plane bit 1), so `coord` equals `merkle_root`. The tip is 7: a height above it does not exist. |
| `reasons` | Every reason code, with the rule it names. |
| `vectors` | The vectors. |

### A vector

| Key | Meaning |
|---|---|
| `name` | Unique, stable. |
| `spec` | The sections the vector exercises. |
| `description` | What the vector shows, in words. |
| `open_question` | Present only when the verdict rests on a reading of the spec that is still open. No vector in this version carries one: the rulings of 2026-10-07 and 2026-10-08 settled every reading the first version left open. |
| `events` | Complete NIP-01 events (`id`, `pubkey`, `created_at`, `kind`, `tags`, `content`, `sig`), kind 3333. Their order is not meaningful: a verifier must resolve them per 8.7.3, and some vectors list them out of order on purpose. Events that are not on the active chain (an older chain, the losing branch of a fork, a branch cut off behind a discarded event) are included where the vector is about ignoring them. |
| `expected` | The verdict. |

Before resolving, a verifier MUST discard every event that is not authentic (8.7.3): it is not a NIP-01 event (`id`, `pubkey`, `sig` and `content` strings, `created_at` and `kind` integers, `tags` an array of arrays of strings, every string encodable as UTF-8), its `id` is not the hash of its canonical serialization, its `sig` is not a valid signature of that `id` by its `pubkey`, its `pubkey` is not `verify_with.identity`, or its `kind` is not 3333. Signatures are always checked, with no option to skip them. Vectors whose names end in `-ignored`, and `forged-event-cuts-branch` and `cut-off-then-continue`, contain such events. Three of them are malformed on purpose: a lone surrogate in `content`, a string `created_at`, and a `null` inside a tag. A port must discard them rather than fail on them; the file is written as ASCII JSON with `\u` escapes so that the lone surrogate can be carried at all.

Resolution, by links alone and before any proof (8.7.3):

- The newest authentic spawn starts the chain. Any `A` tag whose value is `spawn` makes an event a spawn, wherever it stands among the tags; a spawn with a second `A` tag is an invalid newest spawn (`spawn-two-a-tags-*`).
- A spawn is never a link, whatever `e` tags it carries: an older spawn never extends or forks a chain, and the newest spawn's `e` tags are not read (`spawn-never-a-link-old`, `spawn-never-a-link-newest`).
- Forks are counted among distinct events, distinct by id: the same event delivered twice is not a fork (`same-event-twice`).
- The line is Bitcoin mainnet, always (DECK-0001 1.4): a `net` tag on a boarding or ride is never read and not constrained (`ride-net-tag-unread`).
- The chain is followed forward through the first `e previous` tag of each event whose first `e genesis` tag names that spawn. A first copy that names nothing leaves the event unreachable, so it is not on the chain at all (`hop-empty-first-e-previous-unlinked`).
- **A fork is fatal.** When two or more events name the same event as previous, whatever their actions (recognized, skipped or virtual) and whichever is valid or earlier, the verdict is `fork`: `invalid_at` is the spawn, `invalid_index` is 0, `position` is the spawn coordinate (the pubkey), and `chain` runs from the spawn to the event the forking events name. Events never reached, because they descend from a discarded event or name an id nobody holds, cannot make a fork.

Every tag a chain rule reads appears exactly once with a well-formed value. A tag counts by its name alone: a bare `["A"]` is an `A` tag with no value, and a valueless `["X"]` beside a valid `X` makes two `X` tags. On every event, the `A` tag; on every event but the spawn, the `e genesis` and `e previous` tags; on recognized actions, `C`, `c` (not on the exit, whose `c` is never read), the sector tags, `e entry` on an exit, `region` and the `game` p tag on an entry, and the proof tags (`proof`, `mr`, `mp`, `hx`, `hy`, `hz` on a sidestep; `from_height`, `B`, `proof`, `mp`, and `as_of` on a first ride). `mn` may be absent on a sidestep or ride (the exemption lists) but never repeated. Tags no rule reads are free, and inside a bracket and on skipped actions only the `A` and `e` tags are constrained. The `reasons` entry for `malformed` lists exactly what the code checks.

A port MUST check DECK-0001 5.6 (`B` differs from `from_height`) before it checks a ride's proof. `ride-zero-length-first` and `ride-zero-length-later` carry the zero root, zero nonce and empty `mp` of the removed zero-length ride, which no Level 1 check can verify, so a port that checks the proof first reports `hyperjump-proof` where the vectors expect `hyperjump-zero-length`.

A valid verdict:

```json
{"valid": true, "chain": ["<id>", "..."], "position": "<coord hex>", "head": "<id>", "open_bracket": null, "skipped": []}
```

- `chain`: the ids of the active chain in order, the spawn first.
- `position`: the identity's position in cyberspace: the `C` of the last recognized action (8.9 item 5), or the `c` of the `enter-virtual` left open at the head (8.11.4 rule 7).
- `head`: the id of the last event of the active chain, which may be a skipped action.
- `open_bracket`: the id of the `enter-virtual` open at the head, else `null`.
- `skipped`: the ids of the actions skipped under 8.9, in chain order. Names inside a bracket are virtual actions and are never listed here.

An invalid verdict:

```json
{"valid": false, "chain": ["<id>", "..."], "position": "<coord hex>", "reason": "<code>", "invalid_at": "<id>", "invalid_index": 3}
```

- `invalid_at` and `invalid_index`: the first event on the active chain that breaks a rule, and its index in `chain` (the spawn is 0). The chain is invalid from that event, and every event after it counts for nothing.
- `position`: the **last valid position**, where the identity stands frozen until it respawns (3.2, 8.7.3): the position the chain would give it if it ended at the last valid event. That is the `C` of the last valid recognized action, the entry's `c` when the last valid event is inside a bracket, the last recognized `C` when it is a skipped action, and the spawn coordinate (the pubkey) when the spawn itself is invalid or the chain forks.
- `reason`: one code from `reasons`.
- When no authentic spawn exists, `chain` is empty and `position`, `invalid_at` and `invalid_index` are `null`, with reason `no-spawn`.

Each invalid vector breaks exactly one rule, so the order in which a verifier runs its checks on an event does not change the reason, with one exception: the two zero-length ride vectors also carry unverifiable proofs, which is why 5.6 must come before the proof check (above). The free-text detail a verifier prints is not part of the vectors.

### What it costs to run them

Every proof in the vectors is real and checked in full: hops (8.7.1), sidesteps at Level 1 (8.7.2), entry proofs (DECK-0001 3.2) and rides at Level 1 (DECK-0001 5.5). They are kept cheap by construction: the test key was chosen so its spawn has a terrain K of at most 3, every move flips one low bit (spatial trees of height 1), every stop has a terrain K of at most 3, every block's ride leaf is a tree of height at most 10, and every ride is one or two blocks long (re-roll price A = 1). A ride check still replays one height-16 Cantor tree for its price, about a second in pure Python; the whole file verifies in about ten seconds.

### Where the vectors should live

They are here because the reference implementation generates them and runs them on every test run, and because the other vector files the ports already copy (`tests/fixtures/sidestep_v3.json`, `avatar_work.json`) come from this repository. The chain rules are the spec's, not this implementation's, so the file should also be published in arkin0x/cyberspace next to the revision it locks, with this repository and the ports pinned to that copy, as the sidestep and ride references are.
